Subject: Supported persisted REAL-to-Worker fidelity, serialization and independent per-cell evidence

We need to compare complete logical SQLite state through a supported managed D1 read. For every cell whose actual storage class is REAL and whose value is finite binary64, we need its exact readback bits, including either zero sign, its actual type and its original row identity. This includes REAL cells in columns with other declared types. We do not require insertion-intent preservation when affinity legitimately changes the logical persisted value, or physical database-file equality.

The public [REAL-to-Number mapping](https://developers.cloudflare.com/d1/worker-api/#type-conversion), [`raw()` row-array interface](https://developers.cloudflare.com/d1/worker-api/prepared-statements/#raw), and [pinned workerd wrapper](https://github.com/cloudflare/workerd/blob/48e34eaefc8e3ee5633797eebc307ade1cb9642b/src/cloudflare/internal/d1-api.ts) leave the earlier source/serializer boundary unspecified for this purpose. We can encode an already faithful Number using DataView before our application serializes JSON; that does not attest earlier provider conversions. We have no evidence of a managed defect, no universal managed fidelity proof and no account-specific observation to report.

Please answer each question, distinguishing a supported semantic guarantee from an implementation observation or finite test:

1. **API and applicability.** Does supported `env.DB.prepare(fixedSelect).raw()` deliver exactly the logical persisted finite REAL binary64 value, including zero sign, before application code receives it? Does the guarantee cover all finite patterns, subnormals, extremes, exact integers represented as REAL and unexpected REAL cells in non-REAL-affinity columns? Identify exclusions precisely. State whether guarantees differ for raw/all/first/batch, sessions/replicas, REST and direct object SQL; do not imply one API attests another.

2. **Full conversion chain.** Identify the engine value accessor and source representation, each adapter/serializer/parser, and the type/bit semantics at each hop to the delivered Number. For the legacy JSON response, identify the producer, significant-digit/rounding contract and handling of negative zero. Does it emit literal `-0`, normalize it, or provide another supported channel? JSON parsing alone is not evidence of the response encoder's behavior.

3. **Effective JS-RPC.** Is the public `d1_binding_jsrpc` branch available and supported for the relevant managed D1 generations? How can an operator establish the effective branch without relying on an internal flag or selecting a different transport to evade a limitation? Identify the actual service entrypoint/serializer, any prior conversion, supported negative-zero behavior, rollout conditions and a stable applicability reference. General RPC Number support does not identify what Number the database service sends.

4. **Persisted value and zero lifecycle.** Specify affinity/coercion behavior for permissive untyped, BLOB/no-affinity, REAL-affinity and STRICT REAL columns, including insert, commit, fresh read, supported reopen/eviction/restart and restored read. Distinguish normalized persisted `+0` from a persisted `-0` lost in transport. Can either sign be a legal persisted logical REAL after those lifecycles? If an invariant excludes a sign, give its universal supported scope and provenance rather than a finite observation.

5. **Independent channel.** If the full path has no supported all-finite guarantee, is there a supported primitive returning the original cell's type and eight big-endian IEEE binary64 bytes (or equivalent lossless strings) together with row identity, before the questioned formatter/parser? For example, is a source-level `ieee754_to_blob` equivalent supported in managed D1, with a guarantee for both zeros? Identify its API, source, engine applicability and limits. We are not requesting permission to install an extension, move storage, narrow values, change schema or reinterpret `CAST(x AS BLOB)` as raw bytes.

6. **Same-cell identity and snapshot.** How can fixed `SELECT id, typeof(x), x ...` retain original identity, actual type and value from one evaluation? For arbitrary complete-state reads, identify supported handling of hidden rowids, WITHOUT ROWID typed keys, duplicate rows and positional column identity without alias collisions or unsafe integer-to-Number coercion. Explain consistency with the independently closed/quiescent comparison interval; a bookmark alone is not a write barrier. Any separate oracle must bind to the same cell/version and interval, without modifying the compared stores.

7. **Independent persisted-source witness.** Please provide a supported means to observe actual persisted type/bits independently of the channel being qualified, including provenance for oracle independence. An insertion parameter, decimal literal, returned echo, SQL numeric equality, round trip using the same formatter/CAST, second read through the same serializer, or DataView of the delivered Number cannot by itself attest the earlier source bits. For each witness, separate requested insertion bits, actual persisted readback type/bits and delivered Number bits; use explicit unknowns when unobserved.

8. **Small witnesses.** The attached [witness JSON](../../probes/pmb1-managed-real-evidence/witnesses.json) uses bit strings for both zeros, subnormal/normal boundaries, adjacent values, `1e25` and finite extremes. These are candidate inputs, not assertions that insertion preserved their bits. Please state supported construction/readback routes for both zero signs across the affinity/lifecycle matrix. Include INTEGER/REAL/TEXT/BLOB/NULL controls and refusal for nonfinite or unknown states. An inability to construct a witness must remain distinct from proof that no such legal persisted cell exists.

9. **Provenance and invalidation.** Supply stable supported contract/source references; engine version/build or the documented supported version-disclosure refusal; service generation; runtime/compatibility date and effective flags; binding/serializer revisions; rollout scope; and what changes invalidate the answer. State how a later operator can bind those identities to an actual artifact, configuration, schema/query, deployment and observation without substituting a public workerd commit or local emulator version for managed provenance.

10. **Exact answer boundary.** If the guarantee or independent channel is unavailable, explicitly identify the unsupported premise and affected API/generations. If a separate bounded managed observation is needed, describe the supported oracle and required semantics first. A finite passing corpus may detect regressions but cannot supply a universal contract. We will retain complete-reader refusal until applicable positive evidence and independent qualification are reviewed.

The current request is limited to supported semantics and evidence. It contains no private database name, account identity, credentials, production rows, endpoints or requested provider action. A later experiment, new capability, storage decision or contact would require its own exact authorized scope.
