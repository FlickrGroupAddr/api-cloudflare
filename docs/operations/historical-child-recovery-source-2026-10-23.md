# Historical-child recovery source boundary

Date: 2026-10-23. Source implementation; actual recovery remains unprepared.

The [accepted recovery contract](historical-child-recovery-contract-2026-10-23.md)
governs `scripts/historical_child_recovery.py`. The new module prepares the exact
unchanged generic producer's `revoke_expired` plan and approval, and provides a
separately gated delegation boundary. Import and CLI are inert. There is no
installed evidence reader, source importer, namespace writer, credential loader
or network transport, and no affirmative witness or executable template.

The original helper, terminal bytes and timestamps, retirement directory,
historical source, issuance journal and stopped run remain unchanged. The
[original command boundary](post-preparation-command-boundary-2026-10-22.md)
continues to describe that original path. This module does not repoint its bridge.

## Preparation and delegation

1. An independent source/packet review supplies the exact request digest. The
   request identifies a distinct recovery identity, exclusive recovery namespace,
   original run/parent/acknowledged child, one explicit interval, and complete
   role, historical/current evidence and source pins. It has no default facts or
   clock. The code owns the closed field and role inventories.
2. Before any metadata read or producer handoff, the caller's reviewed verifier
   inventories only the exact approved roles, their ancestors, links, aliases,
   private ACLs and SQLite sidecars; it then verifies the full source/import
   closure. A current original `issuer:retire` observation must be unused and
   bound to the original issuance digest and child. Unknown, partial, spent or
   completed states refuse. The verifier may not list/discover runtime paths,
   repair ACLs or substitute credentials.
3. The metadata reader can read only hash-bound historical and current roles.
   The parent and child credential roles are inventory-only. The current witness,
   authority applicability, independent judgment and all original evidence are
   separately authenticated by the trusted verifier. A hash, JSON flag, process
   disappearance, old exit record or elapsed time does not authenticate a fact.
4. Preparation preserves the original plan's security fields and changes only
   operation, interval and three output sinks. Its `issuance` references the
   original journal, original issue-plan digest, exact child, unchanged historical
   active child details. The producer's historical validation reference is the
   retained original issue-plan expiry cutoff, not an observed timestamp or a new
   current observation. The producer's existing validators own provider schemas,
   policies and expiry matching; the
   wrapper does not duplicate or normalize them.
5. An explicit writer atomically reserves the new namespace and durably creates
   three exclusive metadata files: plan, approval and binding. It does not create
   the independent actual packet review. Failed or partial writes leave all
   bytes and namespace occupied; there is no cleanup, retry or overwrite path.
6. Explicit `dispatch(..., execute=True)` rebuilds the packet from its original
   pinned inputs under current inventory and latch gates, verifies the final
   files and independent actual review, reauthenticates current facts, and
   rechecks the latch and current clock immediately before one producer call.
   The operator must supply the reviewed already-verified producer module,
   clock, monotonic clock, transport and credential loader. There are no ambient
   defaults. The concrete boundary constructs the existing `RuntimeInputs` and
   calls the existing `run` exactly once without catch/retry/fallback.

The producer origin, complete producer source map, pinned producer bytes and
finite constants must match. The caller's source verifier also binds the new
controller and the reviewed import graph before any protected reader/importer.
The request keeps `sourceRoot` at the original frozen producer checkout and pins
`controllerSource` separately at the new controller's exact file. The old
checkout does not acquire a new controller file or change its original commit.
Importing the producer before that review is outside this boundary's contract.
Trusted injected code has the operator's authority: a stub verifier that returns
success is synthetic machinery, never proof suitable for an actual run. Producer
`__file__` and constant comparisons are structural checks, not authentication of
loaded code. The supplied module and verifier require separately qualified live
source/import provenance; this source provides no default module authenticator.

## Current evidence and immutable history

The historical terminal is a pinned original input, never a current witness.
The separate witness refers to genuine current identity/custody, complete
consumer **and cleanup-caller** termination, permanent no-readmission and
preserved unknown resources. The verifier authenticates the underlying evidence
and its applicability to the exact request; no boolean assertions are generated
by the wrapper. Original issuance/approval/evidence/journal/review, terminal,
stop/closure/session and source/review pins are retained separately.

Witness observation, authority applicability, independent judgment, actual
packet review and dispatch fit one fixed `[start,end)` interval, positive and
at most 600 seconds. No timestamp is refreshed. Actual parent expiry must outlive
the interval, remain within its accepted lifetime, and be no later than the
unchanged 2026-10-26T12:00:00Z cutoff. The producer revalidates the active parent
under its own live fences. The cutoff alone proves neither validity nor renewal.

Pre-action provider status stays `UNKNOWN`. The unchanged producer checks the
exact child for `expired` status and unchanged historical security fields before
DELETE. Active, disabled, missing, unknown or mismatched observations refuse.
The original producer's atomic single-use `issuer:retire` reservation remains
the retirement fence; the wrapper's earlier observation supplements it and does
not create a second latch. A concurrent contender is still fenced there.

The pinned producer retains five calls maximum: four exact GETs and one
exact-child DELETE, at most 20 seconds per call, at most 8,192 bytes per request,
40,960 total request bytes, 262,144 bytes per response and 1,310,720 total response
wire bytes. It retains durable request intent, unknown-outcome stops and no
replay. No child bearer, resource operation, native input or token creation is
part of this path. These are source limits, not a new executable budget.
